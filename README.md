# pi-longcat

LongCat (Meituan) as a first-class provider for the [pi](https://github.com/earendil-works/pi)
coding agent: `api.longcat.chat`, two models, 1M-token context, CNY billing, a
measured thinking on/off switch, `/login`, a live catalog overlay, and error
paths that reach pi's own retry and auto-compaction machinery.

Built and verified against **pi 1.1.0** (`@earendil-works/pi-coding-agent`,
realpath `~/.nvm/versions/node/v26.10.0/lib/node_modules/@earendil-works/pi-coding-agent`,
typechecked with the global `tsc` 7.1.0-dev.20260823.1 — `npx tsc` does not
resolve a compiler in a bare tree).

Every live claim below carries a date and a method. Raw evidence lives in
[`research/`](research/): the docs capture (`research/doc-*.txt`), every probe
body (`research/probes/`, mirrored as offline fixtures in `test/fixtures/`), the
research notes (`research/notes.md`) and the spend ledger
([`research/probe-ledger.md`](research/probe-ledger.md), generated from
`research/probe-ledger.jsonl`).

## Install

```bash
pi install /path/to/pi-longcat          # or: pi install git:github.com/RarogCmex/pi-longcat
pi                                      # then /login longcat, or export LONGCAT_API_KEY=ak_...
```

Keys are created at <https://longcat.chat/platform/api_keys> (docs: "Your API key
is only shown once upon creation"). The account is **prepaid**: requests are
deducted from the balance in real time and an empty balance is a hard failure
(402 / `insufficient_quota`), which this plugin turns into a message that says
where to top up rather than a key-rotation loop.

Environment variables:

| variable | default | effect |
|---|---|---|
| `LONGCAT_API_KEY` | – | key fallback when nothing is stored via `/login` (stored wins) |
| `LONGCAT_SURFACE` | `chat` | `chat` or `responses`; registers that one adapter. `anthropic` is recognized and refused with the measured reason |
| `LONGCAT_BASE_URL` | `https://api.longcat.chat/openai/v1` | proxy/mirror override, applied to the active surface |
| `LONGCAT_CNY_PER_USD` | `6.7252` (2026-09-15) | FX rate for the cost report |

## Pricing and currency policy

The platform bills in **CNY**, prepaid, deducted in real time, and **only a
successful (HTTP 200) response is billed** — "Failed responses — including HTTP
401, 403, 429, and 500 — will not be charged" (docs, read 2026-10-10). That is
what makes the whole probe ladder in `research/` cheap: a rejected request costs
nothing, and this README's cap numbers come from rejections.

- **Source of the numbers**: `GET /openai/v1/models/{id}` →
  `pricing: {prompt "2", completion "8", cached_tokens "0.04"}` for *both* models
  (recorded 2026-10-10, `test/fixtures/retrieve-2.*.json`). A catalog test
  asserts the curated numbers still equal that body, so a price change fails the
  suite rather than silently mis-reporting cost.
- **Which currency**: the docs publish a USD column ($0.30 / $0.006 / $1.20 per
  1M) and a CNY column (¥2 / ¥0.04 / ¥8) side by side for the same models — the
  international site and the CN site. The machine-readable `pricing` object
  matched the **CNY** column exactly, so these keys bill CNY. (Reading the $
  column instead would understate cost by ~6.7×.)
- **Conversion**: pi's `ModelCost` is USD per million, so the catalog stores CNY
  and converts at a **dated** rate — ¥6.7252 = $1, 2026-09-15, the same rate and
  date the other CNY-billed plugins in this repo use so their cost reports stay
  comparable. Override per session with `LONGCAT_CNY_PER_USD`; rounding is to 6
  decimals so the ¥0.04 cache rate survives as a non-zero `$0.005948`.
- **Cache**: priced as `cacheRead` (¥0.04/1M) because a hit is real and reported
  — measured 2026-10-11 with exactly two identical 836-token requests:
  `cached_tokens` 0 then **768**, i.e. the second call cost ¥0.0002 instead of
  ¥0.0017 (8.6×). `cacheWrite` is 0: no separate write price is published.
- **`promptCache` is deliberately NOT declared.** The cache is implicit and no TTL
  is documented anywhere; pi's cache warmer only fires for models that declare a
  lifetime, so declaring a guessed TTL would make pi send extra *billed* warming
  requests for a cache nobody can keep alive. The economic value is captured by
  pricing `cacheRead` instead.
- **Balance view**: there is none. No balance/credit endpoint is documented or
  reachable with a model key (`/v1/models` at the host root 404s; the platform's
  Usage page is behind a web login), so a plugin cannot show a number. The
  balance error therefore points at <https://longcat.chat/platform> → Billing →
  Recharge and says explicitly that rotating keys cannot help — all keys of one
  account share its balance.
- **Token Packs** (a separate 30-day quota, consumed before the pay-as-you-go
  balance, cache hits free) are invisible to the API and therefore to pi; cost
  reporting here is always the pay-as-you-go rate.

## Thinking

**LongCat thinks by default, and the switch is a binary object, not an effort
scale.**

| probe (all 2026-10-10/11, chat surface, `max_tokens` 8 unless noted) | result |
|---|---|
| no `thinking` field | `reasoning_content` present, `reasoning_tokens: 7` → **thinking is ON by default** |
| `thinking: {"type":"enabled"}` | `reasoning_content` present |
| `thinking: {"type":"disabled"}` | no reasoning, answer `"ok"`, `finish_reason: stop` → **the off switch is honoured** |
| `thinking: {"type":"bogus"}` | accepted (200) and ignored → the vocabulary is not validated, so *acceptance proves nothing* here |
| `thinking: {"type":"enabled","clear_thinking":false}` (pi's exact `zai` bytes) | accepted, reasoning present |
| `reasoning_effort: "high"` | accepted, no observable difference; not in `supported_parameters` ⇒ **not sent** |
| `thinking: {…,"budget_tokens":16}` with `max_tokens` 64 | **ignored**: output ran to 64 ⇒ no reasoning budget field, so none is declared |

Consequences in code:

- `compat.thinkingFormat = "zai"`, because pi's zai branch emits byte-exactly
  `thinking: {type:"enabled", clear_thinking:false}` / `{type:"disabled"}`
  (`pi-ai/dist/api/openai-completions.js:621-623`). The auto-detected `"openai"`
  format would send `reasoning_effort` and **no** `thinking` object — leaving
  thinking permanently on for a model that thinks by default. This is the single
  most important flag in the plugin (`test/wire-format.test.ts` asserts both the
  pinned bytes and what auto-detection would have sent).
- `supportsReasoningEffort = false`, so no effort token is ever sent.
- `thinkingLevelMap` = `{off: "none", low: "low", minimal/medium/high/xhigh/max:
  null}` — pi's picker therefore offers **off** and **low**, and clamps any higher
  request down to `low`. LongCat has one positive state; selling six would be a
  scale the provider does not have. `off` is a *string*, never `null`: `null`
  would hide the level and clamp requests **up** to `low`, billing thinking the
  user turned off. `test/models.test.ts` asserts this against pi's real
  `getSupportedThinkingLevels` / `clampThinkingLevel`.
- On the Responses surface the same map drives `reasoning: {effort: "none"}`,
  which was measured to zero reasoning (output 8 → 2). On the (unregistered)
  Anthropic surface it drives `thinking: {type:"disabled"}`, also measured
  honoured.

**Two side effects of the off switch that are not about tokens** (pitfalls T29:
measure a switch by what it costs you elsewhere):

1. **Vision degrades with thinking off.** Same green 256×256 png, same question:
   `"Green"` + reasoning that describes looking at the image with thinking on
   (`max_tokens` 64); `"White"` with thinking off at 8 tokens and `"Blank white
   rectangular image."` at 32 (2026-10-11). See [Non-chat modalities](#non-chat-modalities).
2. **Reasoning and the answer share `max_tokens`.** With thinking on and
   `max_tokens: 8`, all 8 tokens went to reasoning and `content` was `null` —
   the answer never appeared. pi does not send `max_tokens` by default
   (`pi-agent-core` defaults it to 0 and the adapter omits the field), so this
   only bites when a caller sets a small cap; the gateway offers no budget field
   to bound reasoning with.

`reasoning_content` is parsed by pi into thinking blocks regardless of
`model.reasoning`, which is why the live harness can assert the switch by counting
`thinking` blocks in the assistant message.

## Wire surfaces and routing

The gateway serves **three** wire surfaces. All three were probed live on
2026-10-10/11; two are reachable from this plugin and one is registered.

| surface | endpoint | state as of 2026-10-11 | why |
|---|---|---|---|
| OpenAI Chat Completions | `POST /openai/v1/chat/completions` | **registered (default)** | documented; enforces the output cap; real HTTP statuses on failure; the thinking off switch works even with an image in the request |
| OpenAI Responses | `POST /openai/v1/responses` | **registered behind `LONGCAT_SURFACE=responses`** | real but UNDOCUMENTED — found by probing (`m-spanname: OpenaiController.nativeResponses`; bogus subpaths under the same prefix 404, so it is a registered route, not a catch-all). Buys typed reasoning items and replay; costs four measured defects, below |
| Anthropic Messages | `POST /anthropic/v1/messages` | **checked, works, deliberately NOT registered** | the gateway side is fine (streaming, `tool_use` blocks, thinking on/off all measured). The blocker is on pi's side: its Anthropic adapter authenticates with `x-api-key` (`pi-ai/dist/api/anthropic-messages.js:810-812`) and this gateway answers that header with `401 missing_api_key` (measured 2026-10-11, free). Registering it would need a header-injecting fetch wrapper for no capability the other two lack. `LONGCAT_SURFACE=anthropic` prints that reason instead of silently doing nothing |
| `/openai/native/chat/completions` | – | **checked and absent (2026-10-10)** | the FAQ names this path; it 404s (`{"status":404,"path":"/openai/native/chat/completions"}`). Recorded so nobody re-adds it from the docs |
| `/openai/v1/embeddings`, `GET /v1/models` at the host root | – | **checked and absent (2026-10-10)** | both 404 |

Exactly **one** adapter is constructed per process, so a model can never point at
a surface that was not registered, and the picker shows 2 ids rather than 4 or 6.
The support matrix is uniform (both models answered on all three surfaces), which
is why this is one env switch rather than per-model `api` pinning.

### Why chat is the default and not Responses

The house priority is "OpenAI Responses first", and it is normally right. On this
gateway the measurements say otherwise, and each line below is a recorded probe
(`research/probe-ledger.md`):

1. **It is undocumented.** The platform docs list two formats; `/responses` was
   found by probing. An undocumented route can change without notice.
2. **It does not enforce the output cap.** `max_output_tokens: 131073` was
   *accepted* for a model whose cap is 131072 (and a streaming request with
   `max_output_tokens: -1` was accepted too, then failed as an SSE
   `response.failed` with `usage: 0`). Chat and Anthropic both reject with the
   ceiling named. So the free cap oracle is dead on this surface and a client-side
   bound is the only bound.
3. **It answers some failures with HTTP 200.** A non-streaming invalid field
   returns `200 {"error":{"code":"invalid_prompt",…}}`; `GET /models/{unknown}`
   does the same. pi would read that as an empty stream and report "stream ended
   before a terminal response event" — which pi's retry catalog treats as
   transient, so a permanent error would burn the whole retry budget. `errors.ts`
   re-statuses those bodies, but this surface is the only reason that wrapper
   exists.
4. **Its thinking off switch fails with an image present.** `reasoning:
   {"effort":"none"}` zeroed reasoning for a text-only request (output 8 → 2) but
   not for one carrying an image (output 8, `reasoning_tokens: 7`), while chat's
   `thinking:{"type":"disabled"}` kept working with the same image.
5. **The usual Responses advantage is not one here.** Cache accounting that
   reports hits works on the chat surface too: `cached_tokens` 768 of 836 on the
   second of two identical requests (2026-10-11).

What Responses still buys, measured: `store:false`, `prompt_cache_key` and
`reasoning:{effort,summary}` are all accepted, and pi's exact captured body —
including `include:["reasoning.encrypted_content"]`, which no doc mentions — was
sent live and completed normally (ledger row `R8-responses-pi-exact`). So
`LONGCAT_SURFACE=responses` is a supported configuration, not a experiment; it is
just not the default.

## Non-chat modalities

Three states, each with its own date and source — "not investigated" is never
allowed to read as "absent".

**1. Checked and absent as of 2026-10-10/11**

| modality | evidence |
|---|---|
| embeddings | `POST /openai/v1/embeddings` → 404 |
| image *generation* | no endpoint documented or listed; `GET /models` lists two chat models only |
| audio / speech / video | not documented anywhere in `/platform/docs`; `architecture.output_modalities` is `["text"]` for both models |
| image input on `LongCat-2.0` | `input_modalities: ["text"]`, and measured: an image part was accepted with **zero** effect — `prompt_tokens` 19 with and without a 64×64 png, and the model reasoned "We are given an image? Wait". Accepted-and-dropped, so `input` stays `["text"]` |

**2. Exists and is registered**

- **Image input on `LongCat-2.5-Preview`** (`input: ["text","image"]`).
  Consumption is measured, not assumed: a generated solid-colour png raises input
  tokens 22 → 88 (256×256) → 1393 (1024×1024), and with thinking enabled the
  model named a **green** 256×256 image "Green" and reasoned "Looking at the
  image, it appears to be a solid green color" (2026-10-11). Green was chosen
  because the text-only control for the same question answered "Red" — a red
  target would have been guessable from the prompt alone and would have proven
  nothing.
  Two conditions travel with the claim:
  - **minimum image area**: an 8×8 png is rejected with
    `400 Image too small (area=64px), minimum required area: >256px`, so
    `MIN_IMAGE_AREA_PX = 256` is in `catalog.ts` and `live/check.ts` re-verifies
    the floor for free on every run;
  - **thinking must be on**: the same green image with thinking disabled was
    answered "White" (8 tokens) and "Blank white rectangular image." (32 tokens).
    `catalog.ts` exports that caveat next to the entry, and the live harness runs
    the colour check with thinking on and a 64-token budget.

**3. Deliberately not investigated**

- Whether images are accepted on the **Responses** surface in production: the
  probe was run once (`input_image` with `image_url` as a string, input 103 vs 22
  for text-only ⇒ consumed) but the colour answer was not read there, and the
  surface is not the default. A user who sets `LONGCAT_SURFACE=responses` and
  pastes a screenshot gets an unverified path.
- **PDF / document parts**, **audio input**, and **file uploads**: no endpoint,
  no doc mention, not probed.
- Whether the platform's *web* app capabilities (LongCat Chat, CatPaw agents) are
  reachable with an API key: out of scope for a provider plugin, not probed.
- Tool behaviour on the Anthropic surface beyond the single measured round trip
  (`stop_reason: tool_use` with a `thinking` block, 2026-10-10).

## Compat flags, and why each one is pinned

pi auto-detects OpenAI-compatible behaviour **by URL**, and there is no rule for
`api.longcat.chat` (`pi-ai/dist/api/openai-completions.js:1221-1305`), so the
detected profile is the vanilla-OpenAI one — wrong in six places here. Every flag
is pinned explicitly; `test/wire-format.test.ts` ends with a negative control that
captures the same model with `compat` deleted and asserts the four consequences.

| flag | pinned | auto-detect would say | evidence (all 2026-10-10/11) |
|---|---|---|---|
| `thinkingFormat` | `"zai"` | `"openai"` | pi's zai branch emits byte-exactly `thinking:{type:"enabled",clear_thinking:false}` / `{type:"disabled"}`, the gateway's documented vocabulary, and the sent body was accepted live (`T4`, `R8-chat-pi-exact`). The auto-detected format would send `reasoning_effort` and **no** `thinking` object — leaving thinking permanently on |
| `supportsReasoningEffort` | `false` | `true` | not in `supported_parameters`; sending it returned 200 with no observable difference (`T6`). Accepted-but-nothing-observable ⇒ do not send |
| `supportsDeveloperRole` | `false` | `true` | a 43-token `role:"developer"` message left `prompt_tokens` at the 14-token baseline; the same text as `role:"system"` raised it to 57 (`R2-SYS-*`). The role is silently dropped, i.e. the system prompt would vanish |
| `maxTokensField` | `"max_tokens"` | `"max_completion_tokens"` | `max_completion_tokens: 4` returned **33** completion tokens (`R7`); the validator names `/max_tokens` and `supported_parameters` lists only `max_tokens` |
| `supportsStore` | `false` | `true` | `store` is not in `supported_parameters` on chat. (On the Responses surface pi sends `store:false` unconditionally and it was accepted — that is the adapter's business, not a flag) |
| `supportsLongCacheRetention` | `false` | `true` | no `prompt_cache_retention` in the contract; the cache is implicit with no published TTL |
| `supportsStrictMode` | `false` | `false` | no `strict` in the contract; matches pi's post-#9816 default, pinned anyway |
| `supportsUsageInStreaming` | `true` | `true` | measured: a final SSE chunk carries `usage` with `stream_options:{include_usage:true}` and `data: [DONE]` follows (`S1`) |
| `supportsFinishReason` | `true` | `true` | measured: `stop`, `length`, `tool_calls` all observed |
| `requiresThinkingAsText` | `false` | `false` | reasoning arrives in `reasoning_content`, which pi parses into thinking blocks |
| `requiresToolResultName` | `false` | `false` | a `role:"tool"` result without `name` was accepted (`TL3`) |
| `requiresAssistantAfterToolResult` | `false` | `false` | a tool result with **no** preceding assistant message was accepted (`R7-tool-result-no-assistant`) |
| `zaiToolStream` | `false` | `false` | `tool_stream` is Zhipu-specific and not in this contract |
| `thinkingTokenBudgetField` | *unset* | unset | `thinking:{…,"budget_tokens":16}` with `max_tokens: 64` ran to 64 (`R7-thinking-budget`) ⇒ ignored, so nothing is declared. Consequence documented under [Thinking](#thinking) |
| `promptCache` | *unset* | unset | implicit cache, no published TTL; declaring one makes pi send extra billed warming requests |
| `inputLimits` | *unset* | unset | the only measured image limit is a minimum area (256 px), which pi's `ModelImageInputLimits` cannot express (it holds `resize`/`maxPerMessage`/`maxPerRequest`). It lives in `catalog.ts` as `MIN_IMAGE_AREA_PX`, is surfaced in the entry's `priceNote`, and is re-checked for free by the live harness |

Responses-surface flags (`RESPONSES_COMPAT`) follow the same rule from the same

## Request shapes: why there is no payload hook

**This plugin has no `before_provider_request` hook, and that is a measured
result rather than an omission.** Three of the thirteen sibling plugins needed
one (parts arrays, blank tool results, a missing reasoning field); the shapes pi
1.1.0 produces here were captured offline through `onPayload` and then sent to
the live gateway:

| pi's shape | live result | ledger row |
|---|---|---|
| user `content` as a **parts array** (the docs say `content` is a `string`) | 200, answered normally | `PA1-content-parts-array` |
| `role:"tool"` result after an assistant tool call | 200 | `TL3-tool-result-role` |
| `role:"tool"` result with **no** preceding assistant message | 200 | `R7-tool-result-no-assistant` |
| blank tool result | pi 1.1.0 substitutes `(no tool output)` itself | – |
| the full captured chat body (tools, `stream_options`, `thinking`) | 200, completed | `R8-chat-pi-exact` |
| the full captured Responses body (`store:false`, `prompt_cache_key`, `reasoning:{effort,summary}`, `include:["reasoning.encrypted_content"]`) | 200, completed | `R8-responses-pi-exact` |

Two tests keep the absence deliberate:

- `test/entry.test.ts` asserts the registered hook set is exactly
  `["message_end","turn_end"]` — adding a payload hook turns it red;
- `test/wire-format.test.ts` asserts the parts array survives to the wire
  unflattened, i.e. nothing in this plugin rewrites what pi built.

Copying a sibling's hook here would fix nothing and would hide a regression if the
gateway ever *started* rejecting one of these shapes; the wire test is where that
would show up first, and the live harness re-checks it against the real gateway.

## Error paths

Step 0 was run before any rewrite was written: each recorded body was driven
through pi's **real** adapters and the composed `errorMessage` read back
(`test/errors.test.ts`, § "what pi composes"). The gateway's envelope survives the
SDK, so pi already gets the status *and* the vendor code
(`401: {"code":"invalid_api_key","message":"incorrect api key",…}`), and pi's own
retry catalog classifies it correctly. There is therefore **no classifier layer**
here — only one transport fix and three narrow rewrites.

**1. In-band HTTP-200 errors (the one real fix).** Two paths answer `200` with an
error body: non-streaming `POST /openai/v1/responses` with an invalid field, and
`GET /openai/v1/models/{unknown}`. `remediateInBandResponse` re-statuses them into
the envelope the rest of the gateway uses (mapping the documented codes:
`invalid_api_key`→401, `insufficient_quota`→402, `permission_error`→403,
`rate_limit_*`→429, `server_error`→500, else 400), because a 200 with no
completion makes pi report "stream ended before a terminal response event" —
which is in pi's RETRYABLE list. Guards: status must be 200, content-type must be
JSON (a live `text/event-stream` is never touched), the body must parse into a
top-level `error` object with a message, the read goes through `clone()`, and no
`statusText` is set (an HTTP reason phrase must be Latin-1 and these messages are
Chinese). It is applied to the registered adapter via
`withGatewayErrorRemediation`, which chains onto pi's own fetch and marks itself
with a Symbol so a second registration cannot double-wrap.

Measured scope, so nobody over-trusts it: **streaming** requests do not hit this
path — a streaming validation failure arrives as a proper SSE `response.failed`
with `usage: 0` (recorded), and auth failures are real 401s on all three surfaces,
streaming included (six probes, all 401). The `mt-gateway-error: true` response
header looks like a perfect marker and is **not**: it is present on successful
non-streaming completions too (20 of 21 recorded 200s), so keying on it would
re-status every working response.

**2. Credential failure → actionable text** (`message_end`, then a TUI-only
persistent entry). Adds the key page, `/login longcat`, the env var, and the fact
that an empty balance is a *different* error — and keeps the original text
verbatim, so pi's classification cannot change (asserted against pi's real
`isRetryableAssistantError` / `isContextOverflow` / `getOverflowPatterns`, in both
directions).

**3. Balance failure → the top-up page** and the sentence that matters
operationally: the key was accepted, so rotating it will not help, and on this
platform every key of one account shares its balance. Keeps `402` /
`insufficient_quota` in the text so pi's non-retryable deny-list still matches.

**4. Overflow → pi's compaction marker.** The documented code is
`context_length_exceeded`, which pi-ai already matches
(`/context[_ ]length[_ ]exceeded/i`), so for the documented body the normalizer is
a **no-op** — asserted, so it can never double-prefix. It exists for wordings pi
does not match (CJK variants), it vetoes rate limits first, and it is idempotent.
**The overflow body itself was never measured**: producing it needs
prompt+max_tokens > 1 048 576 (≈¥2 if accepted), and the free route is closed
because the `max_tokens` ceiling check fires first (fixture
`CAP4-chat-window-plus-1.json`). The fixture used by the test is labelled
DOCUMENTED-NOT-MEASURED in the source.

**What is deliberately not handled:** the malformed-JSON path answers with a
different, non-OpenAI envelope (`{"code":50003,"message":"参数解析出错: …",
"data":"com.sankuai…"}`), which the SDK flattens to a bare status. pi never sends
malformed JSON, so there is no user-facing path to fix; the body is recorded
(`test/fixtures/malformed-json.json`) instead.

**The negative that matters most here:** the measured cap rejection —
`参数校验失败: /max_tokens: 131073 is not less or equal to 131072` — must **never**
become an overflow. It is a bad request, and laundering it into
`context_length_exceeded` would make pi summarize a healthy session in a loop.
Four recorded 400s are asserted against every one of pi's overflow patterns,
before and after the rewrite.

**Support and request ids:** the gateway's trace ids live only in *response
headers* (`m-traceid`, `x-ws-request-id`, `m-spanname`), never in the error body,
so they do not survive into pi's flattened message and cannot be quoted from a
session log. If Meituan support asks for a request id, it has to come from a
direct `curl -D-` reproduction; the README notes this because pi cannot show what
the body does not carry.

## Auth, keys and entitlements

**Flow.** `/login longcat` prints the key page
(<https://longcat.chat/platform/api_keys>), prompts for a secret, trims it (a
trailing newline produces the same opaque 401 as a revoked key), warns without
rejecting if it does not start with `ak_` (key formats change), and then validates
it with **zero inference**: `GET /openai/v1/models` with the candidate key.

That oracle is sound here because validation order was measured: **auth → model →
parameters**. A bad key with an unknown model id still answers 401
(`badkey-unknownmodel`), so the empty-body/invalid-body trick that lies on
gateways which validate the body first (pitfalls A22) is not needed — and the
listing check cannot be fooled by a malformed body either. Measured dialect:
`401 {"error":{"code":"invalid_api_key","message":"incorrect api key"}}` for a bad
key, `"missing_api_key"` for none.

The check **fails open**: a 5xx, a 429, a timeout or an unreachable host saves the
key anyway, because "our probe could not reach the gateway" is not evidence about
the credential. Only 401/403 refuse it, and the refusal message says that an empty
balance is a different error so a correct-but-unfunded key is not misdiagnosed.

**Resolution order.** Stored credential (from `/login`) wins; otherwise
`LONGCAT_API_KEY`; both trimmed. pi hides an unauthenticated provider from the
picker, which is why the curated baseline is always registered — an empty catalog
would show as an empty `--list-models`.

**Nine keys, one behaviour.** `secret.env` shipped nine keys. Measured
2026-10-10/11: all nine return an identical two-model listing *and* generate
identically (`prompt_tokens` 14 / `completion_tokens` 4 on the same prompt, nine
times; ledger rows `K-KEY2`…`K-KEY9`). Nothing in the API exposes an account id,
so "one account with nine keys" and "nine identically-scoped accounts" are **not
distinguishable from here** — recorded as unverified rather than assumed. The
docs support the shared-account reading ("Each user can have up to 100 active API
keys"; the balance is per account, and "Do I need separate API Keys for different
models? No").

Consequence for the design: **no key pool, no rotation, no `filterModels`.** There
is no measured per-key difference to exploit, a pool is a later increment in the
house scope rules, and rotating keys cannot fix the only account-level failure
mode this platform has (an empty balance) — which is exactly what the balance
rewrite tells the user. There is also nothing to gate: both models are paid and
both are listed for every key, so no free-tier filtering applies. Rate limits are
documented as "enforced per API key" with **no published numbers**, and none was
hit at ~10 s pacing over 90 requests.

## What is not verified, and what remains

Stated plainly, so no untested claim reads as a tested one.

**Deliberately not measured (cost-bounded)**

- **The context window (1 048 576).** Both machine-readable sources agree, but
  neither is a measurement, and the free oracle is closed: the `max_tokens`
  ceiling check fires before any context check, so the only way to see
  `context_length_exceeded` is a prompt+max_tokens sum above 1M tokens — a ~4 MB
  upload billed in full if accepted (≈¥2). Not run. Practical consequence: pi
  compacts at `contextWindow − reserveTokens` (default 16 384), and the platform
  *does* enforce prompt+max_tokens ≤ window, so a session sitting right at the
  boundary can be rejected rather than compacted. pi sends no `max_tokens` unless
  a caller sets one, which is what makes publishing the true window usable at all.
- **The overflow error body.** Consequently the exact wording is unknown; the
  fixture used by `test/errors.test.ts` is reconstructed from the documented code
  and labelled DOCUMENTED-NOT-MEASURED in the source. pi already matches
  `context_length_exceeded`, so compaction should work — unproven end to end.
- **402 / 403 quota bodies.** Not reachable without draining an account. The
  rewrite matches the documented codes and the CNY balance wording; the shape is
  unverified.
- **Rate-limit numbers and headers.** "Enforced per API key", no figures, and no
  `Retry-After`/limit headers were seen on any response. No 429 was observed in
  ~100 requests at ~10 s pacing, so the retry path in the harness is untested
  against a real 429.
- **Cache semantics beyond "a hit is reported".** Block size, TTL, minimum
  prefix and whether the Responses surface shares the chat cache: not measured
  (observed: 256 of ~359 tokens cached on a repeat, and 768 of 836 on a longer
  one; a warm prefix from a previous run can make the *first* request hit). No
  cache-hit series was run — the house rule is two short requests, once.

**Not verified at all**

- **The real-pi pass.** `pi install`, `pi --list-models`, `pi -p` per model, a
  multi-turn agent run with tools (read → write → reply), thinking on/off inside a
  session, and the error path in **print mode** were not run for this build: on a
  prepaid platform with no free id an agent run is the largest single spend in the
  whole plan, so it was left for an explicitly approved session. Everything the
  harness covers is the adapter layer and below; the host integration above it is
  unverified. When it is run, use a clean `HOME` plus `-e <plugin>/index.ts`, and
  remember a stored credential from `/login` wins over `LONGCAT_API_KEY`.
- **The Responses surface as a daily driver.** Its checks pass
  (`LONGCAT_SURFACE=responses node live/check.ts --billed` is supported), but no
  multi-turn session, reasoning-item replay, or tool loop was exercised on it.
- **Anthropic surface beyond single calls**: multi-turn replay of `thinking`
  blocks, `tool_result` shape, and whether a `system` parameter is required when
  pi folds system messages. Moot while it is unregistered.
- **Streaming edge cases**: no CRLF/comment-frame dialects were seen
  (`data: {…}` + `data: [DONE]` on chat; `event:`+`data:` on Anthropic;
  `response.*` typed events on Responses), and no truncated stream was observed,
  so the `Stream ended without finish_reason` path is untested.
- **Whether the nine keys are one account.** Not answerable from the API (see
  [Auth](#auth-keys-and-entitlements)).
- **Non-chat modalities listed as "deliberately not investigated"** in
  [Non-chat modalities](#non-chat-modalities) — that state is not "absent".

**Remaining work (in priority order)**

1. the real-pi pass above, once an agent-run budget is approved;
2. a measured overflow body (needs a spend decision, ≈¥2 worst case) and then a
   compaction end-to-end check;
3. `LONGCAT_SURFACE=responses` multi-turn verification before anyone relies on it;
4. re-run `node scripts/extract-fixtures.ts` + the free harness after any platform
   change log entry — the retrieve/listing drift checks are the cheap early
   warning;
5. if the platform ever publishes a reasoning-budget field, wire
   `thinkingTokenBudgetField` (currently measured ignored), because reasoning and
   the answer share `max_tokens`.

## Privacy and retention

Capability claims in a different hat, so the same three states apply.

- **What is sent.** pi's adapters send no provider-specific privacy flags here:
  `store` is *not* sent on the chat surface (`supportsStore: false`, and it is not
  in `supported_parameters`); on the Responses surface pi emits `store: false`
  unconditionally and the gateway accepted and echoed it (ledger row
  `R8-responses-pi-exact`, 2026-10-11). `prompt_cache_key` is sent on Responses
  only, derived by pi from the session id. No `user` / `metadata.user_id` field is
  sent by the completions adapter.
- **Retention: deliberately not investigated.** Nothing was measured about how
  long prompts, completions or cached prefixes are kept, and the docs are silent
  (the only related statements are billing ones: a cache hit is free in a Token
  Pack, and consumption is itemized on the Usage page). So `store:false` here must
  **not** be read as "our prompts are not retained" — it is a request field the
  gateway echoed, nothing more. The implicit prompt cache *does* keep prefix state
  server-side for at least the ~5 minutes between two harness runs (measured
  2026-10-11: a repeated prefix hit for 256 tokens), which is evidence of
  server-side state, not of a retention policy.
- **Data residency / region:** one endpoint (`api.longcat.chat`, Meituan,
  openresty in front of `com.sankuai.friday.lap.proxy`); no regional variants are
  documented. CDN hops are visible in `x-via` / `x-cache` headers
  (`cache.51cdn.com`), i.e. traffic transits a Meituan/ChinaNetcache CDN — noted
  because it is a fact about the path, not a policy claim.
- **Telemetry from this plugin:** none. No analytics, no phones home; the only
  network calls are the model listing during a pi refresh, the `/login` key check,
  and the requests pi itself makes.

## Development

```bash
node scripts/link-pi.mjs      # link pi's own packages into ./node_modules (gitignored;
                              # machine-specific — PI_ROOT=/path/to/node_modules to pin one)
npm run typecheck             # tsc -p tsconfig.json against the symlinked pi types
npm test                      # node --test --import ./test/no-network.ts 'test/*.test.ts'
npm run check                 # both
node live/check.ts            # live, FREE checks only (spends nothing)
node live/check.ts --billed   # + the accepted-call checks, each itemized in the ledger
node scripts/extract-fixtures.ts   # regenerate test/fixtures/ from research/probes/
node scripts/readme-models.ts      # regenerate the model table above
node scripts/ledger-report.ts      # regenerate research/probe-ledger.md from the JSONL
```

Layout and dependency direction (`catalog → models → provider → index`); only
`index.ts` touches the pi runtime, everything else loads under plain `node --test`,
which is what makes the offline suite possible without pi mocking:

```
index.ts      the only pi-runtime-coupled file: imports the adapter factories from
              the compat entrypoint, wires message_end/turn_end, registers one surface
provider.ts   createProvider assembly, /login, the in-band remediation wrapper
catalog.ts    pure data + provenance, the exclusion list, isKnownId
models.ts     catalog -> pi Model: currency, compat, surface/base-URL resolution
discovery.ts  live overlay: never throws, bounded, additive, unknowns-only
errors.ts     in-band re-statusing + three narrow rewrites
test/         offline suite (130 tests) + the no-network preload + generated fixtures
live/check.ts the live harness (free by default, --billed opt-in, asserting ledger)
research/     docs capture, probe bodies, notes, ledger, the research probe runners
scripts/      link-pi, fixture/README/ledger generators
```

`tsconfig.json`'s `paths` block mirrors pi's extension loader, which aliases the
bare `@earendil-works/pi-ai` specifier to pi-ai's **compat** entrypoint (the only
place `openAICompletionsApi` / `openAIResponsesApi` are exported). Without the
mirror, `tsc` reports those symbols missing on code that runs fine inside pi.
Subpaths other than `/compat`, `/oauth` and `/providers/all` are **not** aliased,
so they are used only in tests and `live/` (which run under real Node resolution).

`secret.env` is ignored from commit #1 and `test/secret-hygiene.test.ts` scans
every shipped file for key-shaped material, for 12-character windows of any real
key present in `secret.env`/the environment, and for hardcoded user paths. Docs
and tests quote redacted prefixes only (`ak_2uz…`).
